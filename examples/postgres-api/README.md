## Native development

```sh
go mod tidy
cp .env.example .env
set -a; . ./.env; set +a
# Start PostgreSQL and create an app database/user matching DATABASE_URL first.
make migrate-up
go run ./cmd/server
```

The application loads exported environment variables; it does not parse `.env` automatically. The supplied values are local development examples. Use deployment-managed secrets and TLS for external services in production. No credentials or configuration URLs are logged.

```sh
curl http://localhost:8080/health
curl http://localhost:8080/ready
go test ./...
go build ./cmd/server
```

`/health` is liveness; `/ready` pings enabled dependencies with a two-second deadline. No external services are needed for the default unit tests. Generated CRUD integration tests explicitly require `TEST_DATABASE_URL`; Redis integration tests require `TEST_REDIS_URL`; cache unit tests use the real client against an in-process RESP fixture. Tests skip with an explanation when these variables are absent. Use a disposable database: integration tests create/drop their own tables and migration example tests insert/delete rows.

## Docker

```sh
cp .env.example .env
docker compose up --build
docker compose down
```

Compose builds a non-root application, starts only selected services, checks dependency health, runs migrations as a separate one-shot service before HTTP startup, and persists stateful services in named volumes. Native PostgreSQL/Redis ports are bound only to loopback; HTTP is bound to loopback by default in Compose. `docker compose down` keeps volumes; removing volumes destroys local data. The pinned builder/runtime tags should be refreshed as part of maintenance.
After adding a resource, rebuild the migration image: `docker compose build`, then `docker compose run --rm migrate`. Restart/rebuild the app to pick up new routes.

## Architecture and endpoints

`cmd/server` explicitly constructs and closes dependencies. `internal/config` validates environment values. `internal/api` contains response envelopes and validation. `internal/server` owns the selected framework, middleware, health and route registration. Domain packages contain DTOs, a service with injected storage, framework-specific handlers and tests. Only persistent resources contain PostgreSQL repositories. HTTP drains before external clients close. Request IDs are generated per request; logs include method, path, status and duration without bodies or query strings. Gin trusts no proxies by default. CORS has no wildcard/credentials default. Bodies are limited to 1 MiB; unknown JSON fields and trailing JSON are rejected.

```sh
gbme add endpoint users --fields name:string,email:string --method GET,POST --verify
gbme add resource products --fields name:string,price:float64 --crud --verify
make migrate-up
```

Routes use `/api/v1/NAME`. GET supports `limit` (1–100, default 20) and `offset` (0–1000000); persistent resources also support GET/PUT/DELETE at `/api/v1/NAME/{id}`. POST returns 201; DELETE returns 204; invalid input returns 400; missing records return 404. PUT fully replaces fields, including zero/false values. String fields are required and capped at 255 characters; a field named `email` receives email validation. Numeric fields allow zero/negative values: add domain-specific constraints as needed. PATCH is deferred. In-memory endpoints are demonstration storage, reset on restart and limited to 10,000 records; they are not persistent databases. GET-only endpoints initially return an empty list.

Examples are public and unauthenticated. Add authorization appropriate to your application before exposing sensitive data. No authentication capability is advertised by this generator.


## Migrations and transactions

The pinned golang-migrate CLI is invoked reproducibly by Make; initial use needs network access. `make migrate-up`, `make migrate-down` (one version), and `make migrate-status` operate on exported DATABASE_URL. Create an editable migration pair with `NAME=add_index make migrate-create`. Review SQL before applying. Numbered up/down SQL lives in `migrations`; application startup never changes schemas automatically. The `notes` schema/repository is a small parameterized-query and transaction example; resource generation adds typed columns and migrations. `database.Transaction` rolls back on error or panic. Resource updates/deletes use affected-row checks. Migration availability is separate from dependency readiness.


## Editing generated code and pruning

`.gbme.json` records choices, resource specifications, feature dependencies and SHA-256 file ownership plus shared integration files. Keep it in version control. `gbme add` checks the generated route registry before replacing it, preserves all other existing code, and rejects duplicates/symlinks. Put custom route registration in `server.go`; keep `resources_gen.go` generated. There is no automatic removal command. For manual/AI pruning, inspect feature requirements, remove initialization/routes/config and owned files together, run `go mod tidy`, and test/build. Ownership does not imply it is safe to delete modified files.

## Troubleshooting

Connection errors: verify exported URLs, service availability and TLS settings. Native connections use localhost; Compose uses service names. Bind errors are fatal and return a nonzero status. Missing go.sum entries: run `go mod tidy`. A modified registry blocks `gbme add`: preserve your changes in `server.go` and restore the tracked generated registry before retrying. Do not remove `.gbme.lock` while another generator is running.
